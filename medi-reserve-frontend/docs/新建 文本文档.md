# MediReserve 智慧医疗平台 —— 面试高频问题与详细解答

> 本文档涵盖项目全部核心技术点，按模块分类整理，每个问题均提供详细解答。建议面试前通读并理解，可应对 80% 以上的技术追问。


## 一、项目整体架构

### 1.1 项目概述

**Q：请简单介绍一下你这个项目。**

**A：** MediReserve 是一个基于 Spring Boot 3 + Vue 3 构建的智慧医疗预约挂号平台，采用患者端、医生端、管理端三端分离架构，覆盖挂号、支付、评价、在线问诊完整闭环。项目后端 5 个模块、约 2.1 万行代码，前端 80+ 个 Vue/TS 文件。核心解决高并发号源扣减、实时医患沟通与精细化权限管理问题。


### 1.2 技术选型

**Q：为什么选择 Spring Boot 3 和 JDK 17？**

**A：**
- Spring Boot 3 基于 Jakarta EE，对现代 Java 生态支持更好
- JDK 17 是 LTS 版本，提供 Record、Switch 表达式、Text Blocks 等新特性
- Spring Boot 3 最低要求 JDK 17，二者搭配是最新稳定组合
- 项目使用 Maven 多模块管理，便于代码复用和独立部署


### 1.3 模块划分

**Q：为什么要分成 5 个模块？**

**A：**
- **medi-common**：公共模块，实体、DTO、工具类、配置、拦截器等，被所有模块依赖
- **medi-patient**（端口 8081）：患者端，独立部署，支撑高并发挂号场景
- **medi-doctor**（端口 8082）：医生端，排班管理和数据统计
- **medi-admin**（端口 8083）：管理端，审核和运营管理
- **medi-websocket**（端口 8084）：WebSocket 服务，在线问诊实时通信

**优势**：
1. **独立部署**：各端可单独扩容，患者端流量大时可多实例部署
2. **故障隔离**：一个模块宕机不影响其他模块
3. **团队协作**：不同团队可并行开发不同模块

## 二、认证与权限

### 2.1 JWT 认证流程

**Q：JWT 认证是怎么实现的？**

**A：** 四层架构：
1. **生成 Token**：用户登录成功后，`JwtUtil.createToken(userId, username, role)` 生成 JWT，包含 `userId`、`username`、`role`、签发时间、过期时间（2 小时）
2. **Token 传递**：前端存储在 `sessionStorage`，每次请求在 Header 携带 `Authorization: Bearer xxx`
3. **拦截器校验**：`JwtTokenInterceptor` 拦截所有请求，解析 Token，校验有效期和签名
4. **上下文传递**：解析后将 `userId`、`role` 存入 `request.setAttribute`，Controller 通过 `@RequestAttribute` 直接获取


### 2.2 自定义权限注解

**Q：`@RequireRole` 和 `@RequirePermission` 是怎么工作的？**

**A：**

**`@RequireRole`**：标注在方法或类上，指定允许的角色列表（如 `@RequireRole("PATIENT")`）。拦截器解析 JWT 中的 `role` 字段，与注解值做匹配，任一匹配即放行。

**`@RequirePermission`**：标注在方法上，指定需要的权限代码（如 `@RequirePermission("admin:audit:approve")`）。拦截器根据 `role` 查询对应的 `permission_codes` 集合，判断是否包含该权限。

**优先规则**：方法上的注解优先于类上的注解。如果方法上没写，再看类上有没有。


### 2.3 登录失败锁定

**Q：登录失败锁定是怎么实现的？**

**A：** 基于 Redis 实现：
- Key 格式：`login:fail:{username}`
- 阈值：5 次失败
- 锁定时长：15 分钟
- 每次失败 `increment()`，第一次失败时设置过期时间
- 达到 5 次后抛出 `AccountLockedException`
- 登录成功调用 `loginSucceeded()` 删除 Key


### 2.4 BCrypt 加密

**Q：为什么用 BCrypt 而不是 MD5 或 SHA？**

**A：**
- BCrypt 是**自适应哈希**，每次加密结果不同（内置盐值）
- 可配置强度系数（本项目用 10），随着硬件性能提升可调高
- 抗彩虹表攻击和暴力破解
- 使用 Spring Security 的 `BCryptPasswordEncoder`，校验用 `matches()` 方法


### 2.5 多端串号隔离

**Q：多个端同时登录会串号吗？怎么解决的？**

**A：** 会，因为所有端共享同一个 `localStorage`。解决方案：
- 将存储从 `localStorage` 改为 **`sessionStorage`**（每个标签页独立）
- 路由守卫中增加**角色匹配校验**：访问 `/patient` 要求 `role === 'PATIENT'`，不匹配则清除 token 并跳转对应登录页
- 各端 API 实例独立（`patientInstance`、`doctorInstance` 等）


## 三、挂号核心业务

### 3.1 防超卖机制

**Q：如何防止号源超卖的？**

**A：** **双重防超卖机制**：

**第一道防线：Redisson 分布式锁**
- 锁 Key：`lock:schedule:{id}`（每个排班一把锁）
- `tryLock(3秒等待, 15秒持有)`
- 保证同一时刻只有一个线程能操作该排班

**第二道防线：数据库乐观锁**
```sql
UPDATE schedule SET remaining_count = remaining_count - 1 
WHERE id = ? AND remaining_count > 0
```
- 检查影响行数，如果为 0 说明号源已被抢光
- 即使分布式锁失效，乐观锁仍能保证数据一致性

**为什么需要双重？** 分布式锁在极端情况（网络抖动、锁超时）可能失效，乐观锁作为最后兜底。


### 3.2 分布式锁参数设计

**Q：`tryLock(3, 15, SECONDS)` 的参数是怎么定的？**

**A：**
- **等待 3 秒**：正常抢锁只需几毫秒，3 秒代表系统严重繁忙，此时快速失败比让用户傻等更合理
- **持有 15 秒**：整个数据库操作 + 缓存清除通常在 100ms 内完成，15 秒足够宽松；且 15 秒远小于业务超时（30 分钟），不会因业务逻辑耗时过长导致提前释放


### 3.3 事务与锁的顺序

**Q：`@Transactional` 和分布式锁的执行顺序是怎样的？**

**A：**
1. 先获取分布式锁（在事务开启之前）
2. 事务在方法入口开启（`@Transactional` 在方法执行前开启）
3. 执行业务逻辑
4. 方法返回时事务提交
5. `finally` 块释放锁（事务已提交完成）

**关键**：锁释放必须在事务提交之后，避免事务未提交时锁已释放，导致其他线程读取到未提交的数据（脏读）。


### 3.4 乐观锁 SQL 细节

**Q：`decrementRemainingCount` 的 SQL 是怎么写的？有什么特别之处？**

**A：**
```sql
UPDATE schedule SET 
  remaining_count = remaining_count - 1,
  status = CASE 
    WHEN remaining_count - 1 = 0 THEN 3 
    ELSE status 
  END
WHERE id = ? AND remaining_count > 0
```

**特别之处**：
- `WHERE remaining_count > 0` 是乐观锁条件，保证不会扣成负数
- `CASE WHEN` 自动将剩余为 0 的排班状态改为“已满（3）”
- 保留原有状态（如停诊），不会覆盖


### 3.5 幂等支付

**Q：支付接口怎么保证幂等？**

**A：**
1. **前置校验**：检查预约状态，已支付直接抛 `AppointmentAlreadyPaidException`
2. **乐观锁更新**：
```sql
UPDATE appointment SET status = 1 WHERE id = ? AND status = 0
```
3. 影响行数为 0 → 状态已被修改（已支付或已取消），抛异常
4. 避免重复扣款


### 3.6 预约单号生成

**Q：预约单号怎么生成的？**

**A：**
```java
"APPOINTMENT_" + LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMddHHmmss"))
    + String.format("%04d", (int)(Math.random() * 10000))
```
**格式**：`APPOINTMENT_2026073015301234`（前缀 + 时间戳 + 4 位随机数）


## 四、超时取消（Netty 时间轮）

### 4.1 为什么用时间轮而不是 `@Scheduled` 扫表？

**A：**

| 维度           | `@Scheduled` 扫表  | Netty 时间轮         |
| :------------- | :----------------- | :------------------- |
| **时间复杂度** | O(n) 全表扫描      | O(1) 任务调度        |
| **数据库压力** | 每分钟扫百万级数据 | 零数据库查询         |
| **精度**       | 分钟级             | 100ms 级             |
| **资源消耗**   | 每次扫描消耗 IO    | 内存任务，几乎无消耗 |

**结论**：时间轮每个预约独立任务，到期精准触发，不依赖数据库轮询，适合海量延迟任务。


### 4.2 服务重启后任务丢失怎么办？

**A：** **启动扫描补偿机制**：
```java
@PostConstruct
public void init() {
    List<Appointment> timeoutList = appointmentMapper.findAllPendingTimeout();
    for (Appointment appointment : timeoutList) {
        timeoutService.cancelWithLock(appointment.getId());
    }
}
```
- 查询所有 `status=0` 且 `created_at < NOW() - 30分钟` 的预约
- 逐个执行取消逻辑（带分布式锁，防止多实例重复执行）
- 保证**最终一致性**：无论服务重启多少次，超时预约终会被处理


### 4.3 时间轮参数配置

**Q：时间轮的参数是怎么配置的？**

**A：**
```java
new HashedWheelTimer(100, TimeUnit.MILLISECONDS, 512)
```
- **tickDuration = 100ms**：时间轮每 100ms 走一格，精度 100ms
- **ticksPerWheel = 512**：512 个槽位，环形数组大小
- 内存占用：约 512 个槽位 + 每个任务约 100-200 字节
- 10 万等待任务约占用 20MB，可接受


### 4.4 `@Transactional` 自调用失效问题

**Q：取消逻辑中为什么要用 `@Lazy` 自注入？**

**A：** Spring 的 `@Transactional` 通过 AOP 代理生效。在 `cancelWithLock()` 中直接调用 `this.cancelExpiredAppointment()`，`this` 是原始对象而非代理对象，事务注解会失效。

**解决方案**：
```java
@Autowired
@Lazy
private AppointmentTimeoutService self;

// 调用代理方法，事务生效
self.cancelExpiredAppointment(appointmentId);
```


## 五、缓存体系

### 5.1 缓存架构

**Q：缓存是怎么设计的？**

**A：** 三层架构：

| 层级   | 技术              | 特点                                          |
| :----- | :---------------- | :-------------------------------------------- |
| **L0** | Guava 布隆过滤器  | 拦截不存在的 ID，防穿透                       |
| **L1** | Caffeine 本地缓存 | 进程内，毫秒级响应，最大 500 条，过期 10 分钟 |
| **L2** | Redis 分布式缓存  | 跨实例共享，TTL 由业务指定                    |

**读取流程**：L0（布隆过滤器）→ L1（Caffeine）→ L2（Redis）→ DB（回源）


### 5.2 布隆过滤器

**Q：布隆过滤器是怎么用的？解决了什么问题？**

**A：** 解决**缓存穿透**问题。恶意用户用不存在的 `doctorId=999999` 反复请求，如果没有布隆过滤器，每次都会查 Redis（无数据）→ 查 DB（无数据），DB 压力剧增。

**实现**：
- 启动时加载所有有效医生 ID 到布隆过滤器
- 查询前先检查 `mightContainDoctor(doctorId)`
- 返回 `false` → 一定不存在，直接返回空列表，不查缓存和 DB
- 误判率 1%（10000 条数据约 95KB 内存）


### 5.3 多级缓存读取流程

**Q：`MultiLevelCacheService.get()` 的执行流程是怎样的？**

**A：**
```java
// 1. L1：查 Caffeine
Object cached = localCache.getIfPresent(key);
if (cached != null) return cached;

// 2. L2：查 Redis
Object cached = redisTemplate.opsForValue().get(key);
if (cached != null) {
    localCache.put(key, cached);  // 回填 L1
    return cached;
}

// 3. 回源 DB
T result = supplier.get();
// 写入 L2 + L1
redisTemplate.opsForValue().set(key, result, ttl);
localCache.put(key, result);
return result;
```


### 5.4 泛型反序列化问题

**Q：`PageInfo<DoctorListVO>` 缓存时遇到什么问题？怎么解决的？**

**A：** **问题**：`PageInfo<DoctorListVO>` 存入 Redis 再读取时，Jackson 不知道泛型的具体类型，反序列化后变成 `LinkedHashMap`，强转 `PageInfo` 会报错。

**解决**：通过 `TypeReference` 捕获泛型类型：
```java
new TypeReference<PageInfo<DoctorListVO>>() {}.getType()
```
利用 Jackson `TypeFactory` 将 `LinkedHashMap` 精准转换为 `PageInfo<DoctorListVO>`。


### 5.5 SCAN 替代 KEYS

**Q：批量删除缓存时为什么用 SCAN 而不是 KEYS？**

**A：** Redis 的 `KEYS` 命令会扫描全库匹配的 Key，在数据量大时（> 10 万）会阻塞 Redis 主线程数秒，导致所有请求超时。

**解决方案**：
```java
// 使用 SCAN 游标迭代 + 批量 DEL（每批 1000 个）
connection.scan(ScanOptions.scanOptions().match(pattern).count(100).build())
```
- `SCAN` 非阻塞，每次只返回少量 Key
- 分批删除，不影响 Redis 正常服务


### 5.6 缓存空值

**Q：为什么要缓存空值？**

**A：** 防止缓存穿透。当 DB 查不到数据时，也缓存 `null`（有效期 10 分钟），后续请求在 Redis 阶段就直接返回 `null`，不再穿透到 DB。对于不存在的 `doctorId`，布隆过滤器已拦截大部分，空值缓存作为第二道防线。


## 六、WebSocket 在线问诊

### 6.1 为什么用 STOMP？

**Q：为什么用 STOMP 而不是原生 WebSocket？**

**A：**
- STOMP 提供**消息路由**（发送到 `/app/chat.send`，订阅 `/topic/room/{id}`）
- 支持**订阅/发布模型**，天然适合房间隔离
- 提供**点对点消息**（`/user/{userId}/queue/messages`）
- 兼容 **SockJS** 降级方案（不支持 WebSocket 的浏览器用 HTTP 长轮询）


### 6.2 房间隔离

**Q：不同问诊室的消息是怎么隔离的？**

**A：** 每个 `appointmentId` 对应一个 Topic：
```
订阅：/topic/room/{appointmentId}
广播：/topic/room/{appointmentId}
```
- 前端连接时订阅该房间的 Topic
- 后端发送消息时广播到该 Topic
- 只有订阅了该 Topic 的用户才能收到，自然隔离


### 6.3 离线消息补发

**Q：用户断线后消息会丢失吗？怎么补发？**

**A：**
1. 发送消息时，后端判断接收者是否在线（Redis 查询 `ws:user:{userId}`）
2. 不在线 → 消息存入 Redis List `ws:offline:{userId}`
3. 用户重新上线时（`SessionConnectEvent` 监听），从 Redis 取出所有消息，通过点对点通道 `/user/{userId}/queue/messages` 逐条推送
4. 推送完成后清空 List


### 6.4 连接握手认证

**Q：WebSocket 的 JWT Token 怎么传递的？安全吗？**

**A：** 通过 **URL 参数**传递：`/ws/chat?token=xxx&appointmentId=xxx`。

**为什么用 URL 参数？** SockJS 降级机制（HTTP 长轮询）无法自定义 Header，只能用 URL 参数。

**安全措施**：
1. 生产环境强制启用 **WSS**（WebSocket over SSL/TLS）
2. Nginx 日志中过滤 `token` 参数
3. Token 有效期 2 小时，降低泄露风险


### 6.5 消息方向判断

**Q：消息气泡怎么判断是自己的还是对方的？**

**A：** 根据 `senderId` 与当前用户 `userId` 比较：
```typescript
msg.isSelf = Number(msg.senderId) === Number(userStore.userId)
```
- `true` → 显示在右侧（蓝色气泡）
- `false` → 显示在左侧（白色气泡）


## 七、OSS 文件上传

### 7.1 为什么用 STS 临时凭证？

**Q：为什么不用固定 AK/SK 直接上传？**

**A：**
| 方案         | 安全性            | 权限控制               | 时效性     |
| :----------- | :---------------- | :--------------------- | :--------- |
| 固定 AK/SK   | ❌ 泄露即永久有效  | ❌ 无法细化             | ❌ 永不过期 |
| STS 临时凭证 | ✅ 30 分钟自动过期 | ✅ 动态 Policy 隔离目录 | ✅ 自动失效 |

**本项目方案**：前端直传 OSS + STS 临时凭证 + 最小权限 Policy。


### 7.2 Policy 权限隔离

**Q：怎么保证医生只能上传到自己的目录？**

**A：** 动态构建 Policy，将 `doctorId` 硬编码到资源路径：
```json
{
  "Version": "1",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["oss:PutObject"],
    "Resource": ["acs:oss:*:*:medi-reserve-files/medi/doctor/123/*"]
  }]
}
```
- 医生 123 的凭证只能上传到 `medi/doctor/123/` 目录
- 即使前端篡改路径，OSS 校验 Policy 会拒绝


### 7.3 ACL 问题解决

**Q：OSS 上传时遇到权限问题怎么解决的？**

**A：** 阿里云 OSS 默认**阻止公共访问**，即使上传时设置 `public-read` 也会被拒绝。

**解决方案**：
1. OSS 控制台关闭“阻止公共访问”
2. 设置 Bucket 为“公共读”
3. 前端上传时**不设置 ACL 头**，文件继承 Bucket 的公共读权限
4. 后端 Policy 需包含 `oss:PutObjectAcl` 权限（如果设置 ACL 头）


## 八、特色算法

### 8.1 热门医生排行榜（时间衰减算法）

**Q：热门医生排行榜是怎么计算热度的？**

**A：** **时间衰减算法**：
```sql
hotScore = AVG(score * POW(0.98, DATEDIFF(NOW(), created_at)))
```
- 0.98 为衰减系数（每天衰减 2%）
- 30 天前的评价权重只有 54.5%（0.98^30）
- 只统计近 30 天的评价
- 使用 `AVG` 而非 `SUM`，避免评价多的医生绝对占优

**半衰期约 34 天**：适合医疗场景（口碑以月为单位变化）。


### 8.2 智能号源推荐

**Q：智能推荐号源的算法原理是什么？**

**A：** 基于历史就诊率动态调整：
1. 查询该医生过去 4 周同一天（如周三）的平均就诊率
2. 就诊率 = 实际就诊数 / 总号源数（用“就诊数”而非“预约数”，排除爽约）
3. 调整策略：
   - ≥ 85% → 加号 20%（供不应求）
   - ≤ 40% → 减号 20%（供过于求）
   - 40% ~ 85% → 保持不变
4. 边界保护：[1, 100]
5. 无历史数据（新医生）→ 返回用户输入值


### 8.3 为什么用就诊率而非预约率？

**A：** 预约数包含爽约患者，不能反映真实医疗资源消耗。例如预约 18 人但 3 人爽约，实际就诊 15 人，就诊率 75%。如果只看预约数（90%），会误判为供不应求而加号，实际浪费了号源。


## 九、多端隔离与路由守卫

### 9.1 路由守卫设计

**Q：路由守卫是怎么设计的？**

**A：** 守卫逻辑（按顺序）：
1. **管理端**：`/admin` → 检查 token 和角色（`ADMIN` / `SUPER_ADMIN`）
2. **医生端**：`/doctor` → 检查 token 和角色（`DOCTOR`）
3. **患者端**：`/patient` → 检查 token 和角色（`PATIENT`）
4. **问诊室**：`/consultation` → 检查 token 和角色（`PATIENT` / `DOCTOR`）

**角色不匹配时**：清除 token 并跳转到对应端的登录页。


### 9.2 sessionStorage vs localStorage

**Q：为什么用 sessionStorage 而不是 localStorage？**

**A：** `localStorage` 在**所有标签页共享**，多个端同时登录会相互覆盖（最后登录的角色覆盖之前的）。`sessionStorage` **每个标签页独立**，患者、医生、管理端可同时登录，互不影响。


## 十、部署与性能优化

### 10.1 Vite 代理配置

**Q：前端怎么解决跨域问题的？**

**A：** Vite 代理配置：
```typescript
server: {
  proxy: {
    '/api-patient': { target: 'http://localhost:8081', rewrite: ... },
    '/api-doctor': { target: 'http://localhost:8082', rewrite: ... },
    '/api-admin': { target: 'http://localhost:8083', rewrite: ... },
    '/api-websocket': { 
      target: 'http://localhost:8084', 
      ws: true,  // WebSocket 需要
      rewrite: ...
    }
  }
}
```
前端请求 `/api-patient/patient/login` → 代理转发到 `http://localhost:8081/patient/login`


### 10.2 数据统计看板自动刷新

**Q：管理端数据统计看板怎么实现自动刷新的？**

**A：** 使用 `setInterval` 定时轮询：
```typescript
const REFRESH_INTERVAL = 60 * 1000  // 60 秒
refreshTimer = setInterval(() => {
  if (!document.hidden) {  // 仅当页面可见时刷新
    loadAllData()
  }
}, REFRESH_INTERVAL)
```
- 合并所有数据加载到一个函数 `loadAllData()`
- 组件卸载时清除定时器，防止内存泄漏


## 十一、项目难点与解决

### 11.1 最大的技术难点是什么？

**A：** **挂号核心流程的并发控制**：
- **难点**：多个患者同时抢最后一个号源，保证零超卖
- **解决**：分布式锁 + 乐观锁双重保障，锁释放必须在事务提交之后
- **验证**：压测 100+ 并发，remaining_count 始终为 0 时返回“号源不足”


### 11.2 时间轮任务丢失问题

**A：** 服务重启后内存任务全部丢失。通过 `@PostConstruct` 启动扫描数据库补偿执行，保证最终一致性。


### 11.3 多端串号问题

**A：** 所有端共享 localStorage，登录一个端后刷新另一个端会串号。通过 sessionStorage + 路由守卫角色校验解决。


### 11.4 WebSocket 连接失败

**A：** Vite 代理默认不处理 WebSocket 升级。在 `/api-websocket` 代理中添加 `ws: true` 解决。


### 11.5 OSS 图片无法显示

**A：** Bucket 私有导致图片无法访问。关闭“阻止公共访问” + 设置 Bucket 为“公共读” + 上传时不设置 ACL 头。
